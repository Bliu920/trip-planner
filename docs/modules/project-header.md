# Project header

Status: implemented and verified locally.
Owner: project navigation, content toggle, name and ID controls.
Last updated: 2026-10-28.

## Purpose and boundary

`lib/project-header/index.tsx` exports `ProjectHeader({ trip, onSave, contentVisible, onToggleContent })`. It composes navigation, the content toggle, the editable name and Copy ID. Separate files own renaming, copying and styles. Workspace owns the loaded trip and updates recent projects after a successful rename. Library owns access to the Travel brief; the redundant Trip Details panel has been removed. Workspace owns content visibility, responsive behavior and the last selected view.

## Information model

The existing trip record owns `name` and UUID `reference`. The header receives that record rather than loading another copy. Rename drafts, errors and copy feedback are temporary component state. A missing trip shows a loading title without edit or copy controls.

## Lifecycle and interaction

Click the name itself to open the shared rename dialog. There is no edit icon beside it. Its selected input accepts a trimmed name of 1 to 100 characters. Save persists the name; Cancel, Escape and outside clicks dismiss the dialog. An unchanged name closes without a request. Save failures retain the draft and display an error for retry.

Copy ID writes only the UUID through the Clipboard API. A fixed-width button briefly displays Copied, with no banner or content movement. Clipboard failure opens a dialog with the full ID selected for manual copying. The title receives the remaining header width and truncates only when necessary. On screens at most 480px wide, Copy ID becomes an icon-only 44px button while its accessible label and live copy feedback remain available.

The header uses a larger dark icon without a surrounding border or background. Open and closed states use opposite arrows; keyboard focus changes the icon color without adding a fill. The header icon opens and closes trip content. On desktop, trip content is on the left and chat is on the right; the icon points to the content panel. Its accessible label and expanded state describe the currently visible panel. It is disabled while the project is loading. On mobile it has a 44px target, opens the selected view and returns to chat when closed. The first saved Plan keeps chat visible on mobile until the user opens content.

Opening and closing use a short CSS transition: desktop grid tracks/gap and the content surface animate over 180ms; mobile panels crossfade with a 160ms chat transition. Discrete display transitions retain the outgoing surface until its fade completes. Both desktop grid tracks exist in each state so width can interpolate; the chat keeps its centered closed-state width. Panels remain mounted, hidden surfaces become inert and leave the accessibility tree immediately, and no delayed state/timers are added. Reduced-motion preferences disable transitions. Older browsers without discrete display transitions still retain the same usable open/closed states.

## Public contracts and integrations

Renaming sends `PATCH /api/trips/:reference` with `{ name }`. Omitted notes stay unchanged; explicit notes retain existing validation. POST without notes still initializes them to an empty string. Success calls `onSave` with the returned trip. Workspace updates its state and recent-project cache without remounting chat.

## Storage and access

Uses the existing trips table and reference-based access. No migration or new environment variable is needed. The project ID grants existing read/edit access. Name updates are last-write-wins. This change does not alter access rules or create background jobs.

## Verification

Local trip API tests cover name-only PATCH preserving notes and POST defaults. Lint and typecheck pass. Browser checks used a temporary fixture with mocked storage and clipboard, removed after review: successful rename, failed save with retained draft, cancellation, Escape, outside click, UUID copying, clipboard fallback and 390px mobile layout. Copy feedback preserved the 64px desktop header and content position; mobile header is 56px with no horizontal overflow. The rename action was visually checked after fixing portal button colors. Existing project data was not modified during browser checks.

## Limitations

Initial prompt-based names are generated by the separate [project titles module](project-titles.md). This header owns manual renaming only. No cross-tab live name synchronization. Browser clipboard permissions vary; manual copying is the fallback. Local verification does not prove a deployed database is reachable.
